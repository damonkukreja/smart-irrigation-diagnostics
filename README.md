# Smart Irrigation Diagnostics Platform

A full-stack irrigation diagnostics application that combines deterministic anomaly detection with local AI-assisted explanations.

The system evaluates irrigation telemetry using explicit Java rules, persists diagnostic results in PostgreSQL, and optionally uses a locally hosted large language model to explain verified findings and suggest investigation steps.

The deterministic rules remain the source of truth. The AI layer is intentionally non-authoritative and cannot create or change anomaly classifications.

---

## Overview

The application models a simplified irrigation monitoring workflow:

1. Select an irrigation zone.
2. View telemetry readings for that zone.
3. Run diagnostics on a telemetry reading.
4. Apply deterministic anomaly rules in Java.
5. Persist the diagnostic run and findings.
6. Send only the verified findings to a local LLM.
7. Display deterministic findings, AI-assisted explanation, and inference performance metrics.

If the local AI service is unavailable, deterministic diagnostics still complete successfully.

## Deterministic Diagnostic Rules

The system currently implements five deterministic anomaly rules.

### High Flow

Triggered when:

    valve = OPEN
    AND
    flow > expected flow × 1.20

### Low Flow

Triggered when:

    valve = OPEN
    AND
    flow < expected flow × 0.70

### Pressure Drop

Triggered when:

    valve = OPEN
    AND
    pressure < expected pressure × 0.80

### Low Moisture Response

Triggered when:

    valve = OPEN
    AND
    runtime >= 300 seconds
    AND
    final moisture - initial moisture < expected minimum moisture increase

### Unexpected Flow

Triggered when:

    valve = CLOSED
    AND
    flow > 1.0 L/min

These rules are explicit, deterministic, independently testable, and unaffected by model variability.

## Deterministic vs. AI Responsibilities

A central design decision in this project is that AI is not responsible for determining whether an anomaly exists.

### Deterministic Java Layer

The Java analysis engine determines:

- anomaly classification
- observed value
- expected value
- deviation percentage

Current classifications include:

- `HIGH_FLOW`
- `LOW_FLOW`
- `PRESSURE_DROP`
- `LOW_MOISTURE_RESPONSE`
- `UNEXPECTED_FLOW`

### Local AI Layer

The local LLM receives only the verified findings generated by the deterministic engine.

It is used to:

- summarize verified findings
- make technical results easier to understand
- provide neutral investigation steps

The LLM is explicitly instructed not to:

- add or remove anomaly classifications
- rename or reinterpret anomaly classifications
- invent sensor readings
- invent device states
- invent error codes
- invent system or environmental conditions
- claim that a root cause has been identified
- present hypotheses as verified facts
- directly connect a hypothesis to a verified finding using causal language

This keeps anomaly detection reproducible and testable while still allowing AI to improve usability.

---

## AI Safety Boundary

The AI prompt explicitly treats Java-generated findings as verified facts.

The model is instructed to:

- preserve anomaly classifications
- avoid inventing data
- avoid diagnosing a root cause
- frame possible causes only as hypotheses requiring verification
- avoid causal wording that directly connects a hypothesis to a finding
- phrase investigation steps as neutral verification actions

Example verified finding:

    PRESSURE_DROP
    Observed: 40 PSI
    Expected: 54 PSI

An acceptable AI recommendation would be:

    Inspect pressure regulation components and record whether abnormal behavior is present.

The AI should not claim:

    A failed regulator caused the pressure drop.

## Graceful AI Failure

The deterministic diagnostics system does not depend on Ollama being available.

If local AI inference fails:

    Telemetry
       |
       v
    Deterministic Analysis
       |
       v
    Verified Findings
       |
       v
    Persistence
       |
       v
    AI Request Fails
       |
       v
    COMPLETED_WITHOUT_AI

The deterministic diagnostic findings remain valid and are still returned to the user.

The application displays a fallback message indicating that the AI explanation is unavailable.

This behavior is covered by a unit test in `DiagnosticServiceTest`.

## Inference Observability

Each local AI inference run records:

- model name
- prompt token count
- output token count
- total inference latency
- generation tokens per second
- success or failure
- error message

These metrics are persisted in PostgreSQL and displayed in the Angular dashboard.

Example:

    Prompt Tokens: 301
    Output Tokens: 314
    Total Latency: 4.88 s
    Generation Speed: 77.96 tokens/sec

## Reproducible Demo Data

The backend contains a `DemoDataInitializer`.

On startup, it checks whether irrigation zones already exist.

If data already exists:

    Demo data already present; skipping initialization.

If the database is empty, it creates the synthetic North Lawn zone and demo telemetry readings.

This avoids generating duplicate records on every restart while making a fresh setup easier to reproduce.

## Running the Project

### Prerequisites

Install:

- Java 21
- PostgreSQL
- Node.js
- npm
- Angular CLI
- Ollama

Create a PostgreSQL database named:

    irrigation_diagnostics

### Start the Backend

From the repository root:

    cd backend

Provide your PostgreSQL password through the `DB_PASSWORD` environment variable.

Windows PowerShell:

    $env:DB_PASSWORD="your-postgres-password"
    .\mvnw.cmd spring-boot:run

macOS / Linux:

    export DB_PASSWORD="your-postgres-password"
    ./mvnw spring-boot:run

The backend runs at:

    http://localhost:8080

### Start Local AI

Pull the model if necessary:

    ollama pull qwen3.5:9b

Start Ollama:

    ollama serve

The Ollama API runs at:

    http://localhost:11434

If Ollama is unavailable, deterministic diagnostics continue to function.

### Start the Frontend

Open another terminal:

    cd frontend
    npm install
    ng serve

The Angular application runs at:

    http://localhost:4200

## Key Engineering Decisions

### Why deterministic rules instead of AI classification?

The anomaly thresholds are explicit business rules.

Implementing them in Java makes anomaly classification:

- deterministic
- repeatable
- explainable
- independently testable
- unaffected by model variability

The AI layer is used only where natural-language generation adds value.

### Why use an `AnomalyRule` interface?

Each diagnostic rule implements the same contract.

This allows `TelemetryAnalyzer` to depend on `List<AnomalyRule>` instead of directly depending on specific rule implementations.

New anomaly rules can be added without rewriting the analyzer.

### Why use an `InferenceProvider` interface?

The diagnostics service does not directly depend on Ollama.

Instead, it depends on `InferenceProvider`, with Ollama implemented as one provider.

This improves:

- separation of concerns
- testability
- provider replaceability
- failure simulation

It also allows the local model implementation to change without changing the deterministic diagnostic engine.

### Why persist diagnostic runs?

A diagnostic result represents an event in the system rather than just a temporary calculation.

Persisting diagnostic runs provides:

- history
- auditability
- reproducibility
- association between findings and inference runs
- operational performance tracking

### Why separate deterministic findings from AI explanations?

The two outputs have different levels of authority.

Deterministic findings are generated from explicit software rules.

AI explanations are probabilistic and intended to assist interpretation.

The frontend makes this distinction visually clear so users can understand which output is authoritative.

## Failure Handling

The system is designed to degrade gracefully.

### Missing Telemetry

Returns:

    HTTP 404

### Ollama Unavailable

Returns:

    COMPLETED_WITHOUT_AI

while preserving deterministic findings.

### Frontend API Failure

The Angular interface displays user-facing error messages instead of requiring users to inspect the browser console.
